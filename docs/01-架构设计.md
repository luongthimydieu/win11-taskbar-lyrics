# 01 架构设计

本文说明 v1.1 的整体结构、模块边界、关键时序与设计取舍。实现细节以源码为准：协议函数在 `desktop/core.py` 与 `github-pages/index.html` 中一一对应，二者语义必须保持一致。

## 1. 设计目标与约束

| 目标 | 约束 | 对应实现 |
| --- | --- | --- |
| 跨端同步，但不运维服务器 | 没有公网 IP、没有数据库预算 | GitHub Pages 托管手机端，私密 Gist 当 JSON 数据库 |
| 手机随手记，电脑抬头就能看见 | 不能要求两台设备同一局域网 | 走 GitHub HTTPS API，30 秒轮询 |
| 删除不复活、编辑不互相覆盖 | Gist API 没有事务、没有原子写 | 条目级 `updated_at` + 删除墓碑 + 写前先合并 |
| 提醒不能重复、不能错过 | 电脑可能关机、重启、休眠 | `notified_at` 云端去重 + 24 小时补提醒窗口 |
| 贴合任务栏 | 悬浮窗口总像“贴在桌面上的卡片” | 默认置顶覆盖 + 任务栏背景截图逐像素绘制（视觉融入）；`SetParent` 嵌入保留为实验选项 |
| 任务栏位置稳定 | 分辨率、DPI、多屏、explorer 重启、图标增减 | 像素扫描任务栏空位 ∩ 开始按钮/任务按钮/托盘安全带自动避让 + `offset_ratio` 拖拽记忆 + 5 秒句柄/几何检测 + 物理/逻辑像素换算 |
| 核心逻辑可测试 | CI 里没有图形界面 | `core.py` 不导入 PyQt6，55 个离线单测 |
| 不干扰正常使用 | 不能改系统、不能要管理员 | 普通权限运行（置顶窗口 + 任务栏背景截图，不修改系统）+ 当前用户启动文件夹快捷方式 |

明确的非目标：不做实时协作（秒级冲突合并）、不做端到端加密、不做手机后台推送、不替代专业待办软件。

## 2. 总体数据流

```text

│ 手机端 PWA                    │   HTTPS + Bearer Token        │ GitHub                          │
│ github-pages/index.html       │                               │                                 │
│                               │  GET /gists/{id}              │  私密 Gist                      │
│ localStorage：                │  If-None-Match: <etag>        │  └── taskbar_todos.json         │

└──────────────────────────────┘ ────────────────────────────► └───────────────▲─────────────────┘
                                                                               │

│ MediaWatcher 线程             │ ───────────► │ Qt 主线程：TaskbarWidget                        │
│ 常驻事件循环，每 2 秒：        │              │  - 250ms 刷新文案与重绘                          │
│ SMTC 会话 → 歌名/歌手/进度/暂停│              │  - 1s 检查提醒队列                               │
│ 失败 → 枚举网易云窗口标题      │              │  - 30s 触发同步                                  │
└──────────────────────────────┘              │  - 5s 检测任务栏矩形变化                          │
                                              │  - 右键菜单 / 托盘 / 设置对话框 / 拖拽             │
┌──────────────────────────────┐    Qt 信号    │                                                │
│ NeteaseFetch 线程（每首歌一次）│ ───────────► │                                                │
│ 搜索 → LRC → 高赞评论         │              │                                                │
└──────────────────────────────┘              └───────────────▲────────────────────────────────┘
                                                              │ Qt 信号（sync_finished）
                                              ┌───────────────┴────────────────┐
                                              │ GistSync 线程（同一时刻仅一个）  │
                                              │ 拉取 → mergeDocs → needsPush?  │
                                              │ → PATCH → 回传新文档与新 ETag    │
                                              └────────────────────────────────┘
```

三条独立通路：

1. **媒体通路**：SMTC/窗口标题 → 歌名与播放进度 → 歌词定位；
2. **内容通路**：歌名 → 网易云接口 → LRC 行与热评文本；
3. **同步通路**：本地文档 ↔ Gist ↔ 手机端文档，只走合并协议。

三条通路互不阻塞：网易云挂了不影响同步，GitHub 挂了不影响歌词，媒体后端缺失只影响歌词精度。

### 3.4 前端分层

`index.html` 的内联脚本是一个 IIFE，内部严格分成两层：

- **纯函数层**：从 `SCHEMA_VERSION` 到 `protocol` 对象，不接触 DOM/localStorage，最后挂到 `window.__TBL_PROTOCOL__`；
- **应用层**：`STORAGE_*`、`state`、`getRemote`/`putRemote`/`createGist`、`syncNow`、渲染与事件绑定。

Node 测试直接从 HTML 里抽取最后一个 `<script>`，在 `vm` 沙箱执行，只取 `window.__TBL_PROTOCOL__`，因此应用层代码不会被测试执行。

## 4. 线程与事件模型

Qt 的界面对象只能在主线程操作，所以所有网络与系统调用都放到工作线程，通过信号回主线程。

| 执行体 | 启动方式 | 周期/触发 | 做什么 | 如何回主线程 |
| --- | --- | --- | --- | --- |
| Qt 主线程 | `QApplication.exec()` | 事件驱动 | 绘制、菜单、拖拽、计时器、提醒状态机 | — |
| `MediaWatcher` | `start_media_watcher()` | 常驻，每 2 秒 | SMTC 读取 → 失败则窗口标题 | `bridge.media_updated.emit(dict)` |
| `NeteaseFetch` | 切歌时新建 | 每首歌一次 | 搜索、LRC、热评 | `bridge.lyrics_ready.emit(key, bundle)` |
| `GistSync` | `request_sync()` | 30 秒 + 手动 + 本地变更后 | GET → merge → PATCH | `bridge.sync_finished.emit(result)` |

关键点：

- **媒体线程只创建一次事件循环**。v1.0 每 2 秒在 Qt 主线程调用 `asyncio.run()`，每次新建/销毁事件循环，既卡 UI 又可能泄漏；v1.1 在 `MediaWatcher.run()` 里 `new_event_loop()` 一次，之后 `run_until_complete(self._read_smtc())` 复用。
- **manager 单例**。`GlobalSystemMediaTransportControlsSessionManager` 只在第一次 `request_async()` 时创建，避免反复请求系统权限与枚举会话。
- **同步单飞**。`_sync_running` 保证同一时刻只有一个 Gist 请求在跑；同步开始前对 `self.doc` 做 `json.loads(json.dumps(...))` 快照，避免工作线程读到主线程正在改的对象。
- **同步期间的新改动不丢**。`on_sync_finished` 用 `merge_docs(remote, self.doc)` 把主线程在同步窗口内完成的点击并回来；若产生了本地新内容，2.5 秒后再补一轮推送。
- **图标/托盘只在主线程**。工作线程不碰任何 QWidget。

## 5. 同步时序

### 5.1 手机端写一条待办

```text
用户点“添加”
  └─ protocol.addTodo(doc, fields)
       ├─ 生成 id = td-<毫秒时间戳>-<6位随机>
       ├─ created_at = updated_at = 本地当前时间（ISO8601 带偏移）
       ├─ normalize（非法时间/日期清空）
       ├─ todos 按 id 排序
       ├─ version += 1
       └─ updated_at = now
  └─ applyDoc(next, "已添加…")
       ├─ localStorage["tbl.doc.v2"] = next
       ├─ state.meta.dirty = true
       ├─ renderTodos()
       └─ scheduleSync(900ms)
            └─ syncNow()
                 ├─ GET /gists/{id}（带 If-None-Match: 上次 ETag）
                 ├─ 304 → 用 tbl.remote.v2 缓存；没有缓存则无 ETag 再 GET 一次
                 ├─ 200 → normalizeDoc(云端) 并记下新 ETag
                 ├─ merged = mergeDocs(local, remote)
                 ├─ shouldPush = dirty || needsPush(merged, remote)
                 ├─ PATCH /gists/{id} 写入 merged（缩进 2 的 JSON）
                 └─ 成功：dirty=false，保存 doc/etag/remote/meta，刷新状态
```

### 5.2 电脑端 30 秒轮询

```text
QTimer(sync_sec) / 右键“立即同步” / 完成或稍后提醒后
  └─ request_sync()
       ├─ 未配置 Token 或 Gist ID → 直接返回
       ├─ _sync_running → 丢弃本次（防止重入）
       ├─ snapshot = 深拷贝(self.doc)，etag = self.etag
       └─ GistSync 线程：GitHubGistStore.sync(snapshot, etag)
            ├─ GET（带 ETag）
            ├─ 304 且 _last_remote 为空 → 无 ETag 全量 GET 一次
            ├─ needs_push(local, remote)?
            │    ├─ 是 → merge_docs + PATCH，report.pushed = true
            │    └─ 否 → 不写
            └─ 回传 {doc, remote, pushed, etag}
  └─ on_sync_finished()
       ├─ 失败：记录 last_error、写 state.json、托盘气泡提示一次
       └─ 成功：
            ├─ merged = merge_docs(remote, self.doc)   # 合并同步窗口内的本地点击
            ├─ self.doc = merged，更新 ETag / last_sync
            ├─ save_state(...)
            ├─ refresh_texts() + check_reminders()
            └─ 若本地还有新内容 → 2.5 秒后 request_sync()
```

### 5.3 为什么“写前 GET”是必须的

Gist 的 PATCH 是整文件覆盖。若直接 `PATCH(local)`：

- 手机端刚新增的 B 会被电脑端的旧文档覆盖；
- 电脑端刚删除的条目会被手机端的旧文档复活；
- 两端同时编辑同一条目时，后写者无条件获胜，先写者的内容没有任何合并机会。

v1.1 的顺序固定为 **GET → merge → needsPush → PATCH**。PATCH 的内容永远来自“本地与远端合并后的结果”，因此一次覆盖不会丢失任何一端已经表达过的意图（在条目级 LWW 的语义下）。详细算法见 [03 同步协议](03-同步协议.md)。

## 6. 提醒时序

```text
t0  手机端创建：remind_date=2026-10-18, remind_at=09:00, notified_at=""
      │
t1  电脑端同步到该条目（30s 内）
      │
t2  每秒 check_reminders()
      ├─ upcoming_reminders(doc)：未完成、notified_at 为空、目标时刻已到、且滞后 ≤ 24h
      ├─ 不在队列/不是当前提醒 → 入队
      └─ 当前无提醒 → 出队一条 _activate_next_alert()
            ├─ core.mark_notified(doc, id)  → notified_at = now
            ├─ save_state + request_sync（云端去重，重启不再提醒）
            └─ _compose_texts() 返回 alerting=True
      │
t3  主线程 250ms 重绘：红底 + 0.5Hz 呼吸闪烁，主行“⏰ 到点待办：…”，副行提示操作
      │
      ├─ 左键：complete_alert() → set_done(done_at=now) → 下一条
      ├─ 右键“10 分钟后再提醒”：snooze_todo()
      │     ├─ remind_at = now+10min 的 HH:MM
      │     ├─ remind_date = now+10min 的日期
      │     ├─ notified_at = ""（允许再次提醒）
      │     └─ version+1 → 写回云端
      └─ 右键“本次忽略”：只清当前提醒，不改数据
```

提醒判定只看四个条件：未完成、未提醒过、有合法 `remind_at`、距目标时刻在 `[0, 24h]`。这解决了 v1.0 的三个问题：`HH:MM` 字符串比较把“明天 9 点”当今天立刻提醒；`reminded_ids` 只在内存导致重启重复提醒；只在拉取成功时检查导致离线时永远不提醒。

电脑关机一晚，第二天开机时目标时刻仍在 24 小时窗口内，会补一次提醒；超过 24 小时则不再打扰，条目仍留在待办列表里。手机端只把已到点的条目渲染成红色边框，不做系统通知。

## 7. 歌词时序

```text
MediaWatcher（每 2s）
  ├─ 有 SMTC：选 cloudmusic/netease/163 会话，否则当前会话
  │    ├─ title/artist ← try_get_media_properties_async()
  │    ├─ position ← get_timeline_properties().position
  │    └─ is_playing ← get_playback_info().playback_status == 4
  ├─ 无 SMTC/失败：EnumWindows 找类名 OrpheusBrowserHost / Win32Window
  │    └─ 标题 "歌名 - 歌手"；不要求窗口可见（最小化到托盘也能拿）
  └─ emit {title, artist, position, is_playing, source}
        │
主线程 on_media_updated()
  ├─ song_key 变化 → 清空旧歌词/热评 → 状态 loading → 新线程抓网易云
  └─ 保存 _media_mono = time.monotonic()
        │
NeteaseFetch 线程
  └─ fetch_song_bundle(title, artist)
       ├─ 30 分钟内成功结果直接复用
       ├─ 搜索 song_id → LRC → hotComments（无 hot 时按 likedCount 排序）
       └─ emit lyrics_ready(key, bundle)
        │
主线程 on_lyrics_ready()
  ├─ key 不是当前歌 → 丢弃（已切歌）
  ├─ 成功：_lyrics_state = ok；失败：failed + 错误文本（只影响这两项）
  └─ refresh_texts()
        │
每 250ms 计算位置
  ├─ is_playing 且 SMTC 有进度：position + (monotonic - media_mono)
  ├─ is_playing 但无进度：monotonic - fallback_start_mono（窗口标题兜底）
  └─ 已暂停：冻结在 anchor（不再外推）
        │
core.current_lyric(lyrics, position) → 二分找最后一条时间戳 ≤ position 的行
```

v1.0 用 `time.time()` 墙钟累加，系统对时/休眠恢复会跳变；v1.1 用 `time.monotonic()` 外推，并在暂停时冻结。SMTC 每次 2 秒回填一次 anchor，误差不会累积。

## 8. 关键设计决策与取舍

| 决策 | 原因 | 代价/边界 |
| --- | --- | --- |
| Gist 当数据库 | 免费、免注册、数据在用户自己账号、天然有版本历史 | 无原子写、无 webhook、每小时 5000 次限额、单文件 1MB 截断 |
| 30 秒轮询而非长连接 | 没有服务器可挂 WebSocket | 最长 30 秒延迟；用 ETag 把大部分请求变成 304 省额度 |
| 条目级 LWW + 墓碑 | 比整份覆盖可靠，比 CRDT 简单，两端代码量可控 | 同一秒内的并发编辑仍可能丢一边；墓碑要保留 180 天/200 条 |
| `version` 单调递增 | 方便日志排查“这是第几轮合并” | 它不是并发控制，不参与胜负判定 |
| `canonical` 忽略 `version`/`updated_at` | 否则每轮 merge 都会因元数据不同而误判“需要推送” | 要求两端 JSON 键序、空值、时间格式严格一致 |
| `core.py` 零 Qt | 可在无图形环境跑单测、可被未来 CLI 复用 | 所有 UI 状态要手动经信号搬运 |
| 双媒体后端 | 兼容 Python 3.10–3.13；`winsdk` 没有 cp313 轮子 | 两套 API 名称差异要分别处理，打包时要收集对应包 |
| 窗口标题兜底 | 没装媒体后端也能用 | 无法判断暂停/拖动，歌词只能按单调时钟估算 |
| `offset_ratio` 而非绝对像素 | 换分辨率/缩放后仍落在任务栏相近比例位置 | 不是像素级精确；任务栏按钮布局变化仍可能挡住 |
| 拖拽松手才写配置 | 避免拖动过程中高频写盘 | 拖到一半崩溃会丢这次位置 |
| PWA + Service Worker | 手机可加到主屏幕，离线能打开外壳 | 首次加载仍需联网；数据离线只读缓存，改动靠 dirty 重试 |
| 设置对话框合并 | v1.0 连续弹两个 `QInputDialog`，容易填错 | 对话框代码更长，但可“测试连接/创建 Gist” |

## 9. 限制与安全边界

### 9.1 Token 与隐私

- **Token 只存在本地**：电脑端在 `%APPDATA%\Win11TaskbarLyrics\config.json`（当前用户目录 ACL 保护），手机端在浏览器 `localStorage`；代码只把它放进 `Authorization: Bearer` 发往 `api.github.com`，不写日志、不进 Git 仓库。
- **最小权限**：只创建 classic token 并勾选 `gist`，不要勾 `repo`、`workflow`、`delete_repo`。Token 泄露时在 GitHub **Settings → Developer settings → Personal access tokens** 立即撤销，再在两端重新填。
- **Gist 私密 ≠ 加密**：私密 Gist 不出现在公开列表和搜索里，但知道链接的人可能可以查看；GitHub 服务端能读到明文，拥有你账号访问权的人（或拥有 `gist` 权限的 Token）也能读到。不要放密码、私钥、身份证号、公司机密。
- **网易云请求**：歌名与歌手会作为查询参数发给 `music.163.com`；评论内容来自公开接口。不要用本项目抓取需要登录才能看的内容。

### 9.2 一致性与并发

- Gist API 没有 `If-Match`/事务，两个客户端同时 PATCH 时 HTTP 层仍是“后写覆盖先写”。v1.1 不承诺强一致，只承诺**最终收敛**：被覆盖的一端下一轮 merge 会把自己的内容重新并回去。
- 胜负依据是本机时钟写出的 `updated_at`。两台设备时间相差很大时，慢钟设备的新编辑可能输给快钟设备的旧编辑。建议开启 Windows 自动对时；手机与电脑通常都联网对时。
- 墓碑保留 180 天、最多 200 条。超过窗口的删除记录会被裁剪；如果此时另一台设备离线超过 180 天再回来，旧条目可能复活。
- JSON 损坏或文件被截断时 `get_doc()` 直接抛错，同步停止，**不会用本地数据覆盖坏文件**；修好云端或换 Gist 后再继续。
- 混用 v1.0 与 v1.1：v1.0 只写 `{updated_at, todos}`，不认识 `tombstones`，一次保存就可能把删除记录抹掉。升级必须两端一起换。

### 9.3 平台与外部依赖

- 只用主任务栏 `Shell_TrayWnd`；副屏任务栏、自动隐藏、任务栏在屏幕顶部/左侧、ExplorerPatcher 等第三方工具都可能让位置不准。
- `WindowStaysOnTopHint` 挡不住独占全屏（游戏、部分播放器）和 UAC 安全桌面。
- 网易云接口是非官方公开接口，可能改协议、加风控或限流；失败只降级歌词/热评，不影响核心待办。
- Gist 单文件内容超过 1MB 时 GitHub 返回 `truncated: true`，程序报错并停止同步；定期清理已完成待办。
- 手机端依赖 Service Worker；iOS 需要 Safari「添加到主屏幕」后才更接近独立应用，普通标签页关闭后不会后台同步。

## 10. 故障域与降级矩阵

| 故障 | 影响 | 程序行为 | 恢复方式 |
| --- | --- | --- | --- |
| 网易云接口失败/限流 | 无歌词、无热评 | 只显示歌名；状态记 `failed`，不缓存失败结果 | 切歌或重启程序后重试；换网络 |
| 没有 winsdk/pywinrt | 歌词不精确 | 读网易云窗口标题，按单调时钟推进，暂停不冻结 | 按 [部署指南](02-部署指南.md) 装媒体后端并重启 |
| 未配置 Token/Gist | 无跨端同步 | 本机待办、提醒、歌词全部可用 | 右键配置 |
| Token 401 | 同步停止 | 托盘气泡提示一次，状态写入 `state.json` | 重新生成 Token 并在两端更新 |
| 403 限流 | 同步停止 | 按错误分类提示；304 不消耗额度 | 等到窗口重置；减少手动同步 |
| 404 | 同步停止 | 提示检查 Gist ID | 用「创建新 Gist」重新绑定 |
| 网络断开 | 同步停止 | 本地文档继续可用；手机端保留 dirty | 恢复后下一轮自动重试 |
| Gist JSON 损坏 | 同步停止 | 抛错，不覆盖云端 | 在 Gist 历史里恢复或换新 Gist |
| explorer 重启 | 胶囊位置可能错 | 5 秒内检测任务栏矩形变化并重新吸附 | 自动恢复 |
| 配置/状态文件损坏 | 回到默认 | 记警告日志，使用默认配置/空文档 | 重新配置或删 `%APPDATA%\Win11TaskbarLyrics` |
| 重复启动 | 出现两个胶囊 | 命名互斥量拦截，弹“程序已经在运行了” | 从托盘/任务栏操作，或退出后重启 |
