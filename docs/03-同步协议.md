# 03 同步协议

这是跨端同步的核心文档。桌面端 `desktop/core.py` 与手机端 `github-pages/index.html` 里的 `window.__TBL_PROTOCOL__` 实现的是**同一套协议**：字段名、归一化规则、时间格式、合并胜负、指纹算法都必须一致，否则会出现“每轮都在推送”或“删除被复活”。

## 1. 目标与不变量

协议要保证四件事：

1. **不丢新增**：两端各自新增的条目，合并后都在；
2. **删除可传播**：一端删除后，另一端不会用旧副本把它复活；
3. **同一条目有确定胜负**：按条目级 `updated_at` 后写胜出，不整份覆盖；
4. **可判定“要不要写”**：用内容指纹判断，避免无意义的 PATCH。

不承诺：强一致、秒级实时、跨设备原子事务、冲突内容自动融合（同一条目只保留胜出的整条记录）。

四个核心不变量：

- `todos[*].id` 在文档内唯一；
- `todos` 与 `tombstones` 都按 `id` 升序排列（归一化后）；
- 任何合并结果都满足 `schema = 3`，`version` 为正整数且大于两端输入；
- 同一份内容归一化后，两端 `canonical` 输出必须逐字节相同。

## 2. 存储位置与命名

| 项 | 值 |
| --- | --- |
| 云端容器 | 一个**私密** GitHub Gist（`public: false`） |
| 文件名 | `taskbar_todos.json`（常量 `GIST_FILENAME`，两端一致） |
| API 基址 | `https://api.github.com` |
| 文档 schema | `3`（常量 `SCHEMA_VERSION`） |
| 账本文件 | `taskbar_ledger.json`（独立私密 Gist，常量 `LEDGER_FILENAME`，schema 1） |
| 每日记忆 | 私有仓库 `taskbar-memory` 的 `memories/YYYY-MM-DD.md` + `memories/index.json`（不参与 Gist 同步） |
| 本地缓存（电脑） | `%APPDATA%\Win11TaskbarLyrics\state.json` 的 `doc` 字段 + `etag` |
| 本地缓存（手机） | `localStorage` 的 `tbl.doc.v2` / `tbl.etag.v2` / `tbl.remote.v2` / `tbl.meta.v2` |
| 配置（电脑） | `%APPDATA%\Win11TaskbarLyrics\config.json` 的 `gh_token` / `gist_id` |
| 配置（手机） | `localStorage` 的 `tbl.config.v2`，并镜像到 v1 键 `gh_token` / `gh_gist_id` |

Gist 里只有这一个文件；手机端与电脑端都读写同一个文件名，不通过 Gist 描述或其它文件传状态。

## 3. 完整 JSON Schema

### 3.1 示例文档

```json
{
  "schema": 2,
  "version": 42,
  "updated_at": "2026-10-17T18:30:00+08:00",
  "todos": [
    {
      "id": "td-1760697000000-a1b2c3",
      "text": "交周报并复盘项目进度",
      "priority": "high",
      "done": false,
      "created_at": "2026-10-17T09:00:00+08:00",
      "updated_at": "2026-10-17T09:00:00+08:00",
      "remind_at": "18:00",
      "remind_date": "2026-10-18",
      "notified_at": "",
      "done_at": ""
    }
  ],
  "tombstones": [
    {
      "id": "td-1760600000000-9f8e7d",
      "deleted_at": "2026-10-17T10:00:00+08:00"
    }
  ]
}
```

字段的书写顺序不影响语义。`put_doc()` 落盘时用 `json.dumps(..., ensure_ascii=False, indent=2)`，条目按归一化后的插入顺序输出；`canonical()` 会用 `sort_keys=True` 重新排序，所以两端比较不依赖文件里的键序。

### 3.2 顶层字段

| 字段 | 类型 | 必有 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `schema` | 整数 | 是 | 固定 `2` | 协议版本；归一化时强制写成 2 |
| `version` | 整数 | 是 | ≥ 0 | 文档版本号；每次本地变更/合并 +1，仅用于排查与日志，不参与胜负 |
| `updated_at` | 字符串 | 是 | ISO8601 带时区，秒级 | 文档最后一次生成/合并时间；不参与指纹 |
| `todos` | 数组 | 是 | 元素为待办对象，`id` 唯一 | 当前存在的待办 |
| `tombstones` | 数组 | 是 | 元素为 `{id, deleted_at}` | 删除墓碑；用于阻止旧副本复活 |

### 3.3 待办条目字段

| 字段 | 类型 | 必有 | 归一化规则 | 含义 |
| --- | --- | --- | --- | --- |
| `id` | 字符串 | 是 | 缺失或空值时生成 `td-<毫秒时间戳>-<6位十六进制>`；非空值原样保留（不做格式校验） | 全局唯一标识，手机与电脑生成的 id 不冲突 |
| `text` | 字符串 | 是 | 去首尾空白；空文本的条目被丢弃 | 待办内容；兼容 v1 的 `title` / `content` |
| `priority` | 字符串 | 是 | `high` 或 `normal`；其它值一律 `normal` | 紧急/普通；影响排序与图标 |
| `done` | 布尔 | 是 | `bool(value)` | 是否完成 |
| `created_at` | 字符串 | 是 | ISO8601；无法解析用 `1970-01-01T00:00:00+00:00` | 创建时间；无 `remind_date` 时也用作提醒日期锚点 |
| `updated_at` | 字符串 | 是 | ISO8601；缺失时退化为 `created_at` | 条目级最后修改时间；合并胜负的唯一依据 |
| `remind_at` | 字符串 | 是 | 必须是 24 小时制 `HH:MM`（小时 00–23、分钟 00–59）；否则 `""` | 提醒时刻（本地墙钟，不带时区） |
| `remind_date` | 字符串 | 是 | 必须匹配 `^\d{4}-\d{2}-\d{2}$` 且是合法日期；否则 `""` | 提醒日期（本地日历日） |
| `notified_at` | 字符串 | 是 | ISO8601；空字符串表示未提醒 | 已提醒时间；非空即抑制再次提醒，跨端去重 |
| `done_at` | 字符串 | 是 | ISO8601；`done=true` 且缺失时取 `updated_at` | 完成时间；未完成时为 `""` |

空值约定：所有时间字段用 `""` 表示“没有”，不用 `null`；布尔用 `true/false`；数组永远存在（可以是 `[]`）。归一化会丢弃未知字段，因此不要依赖协议之外的扩展字段在同步后仍然存在。

`remind_at` 的校验等价于正则 `^([01]\d|2[0-3]):([0-5]\d)$`；`remind_date` 的校验等价于 `^\d{4}-\d{2}-\d{2}$` 且 `date.fromisoformat` 能解析。

### 3.4 墓碑字段

| 字段 | 类型 | 必有 | 约束 | 含义 |
| --- | --- | --- | --- | --- |
| `id` | 字符串 | 是 | 与待办 `id` 对应 | 被删除条目的标识 |
| `deleted_at` | 字符串 | 是 | ISO8601，秒级；缺失的墓碑整条丢弃 | 删除发生时间；与条目 `updated_at` 比较决定删除是否生效 |

墓碑只记录“删除”这一事实，不保留被删内容。客户端看到墓碑后删除本地同 id 条目；墓碑本身保留 180 天、最多 200 条，之后被裁剪。

### 3.5 v1 兼容映射

| v1 字段/形态 | v2 字段 | 说明 |
| --- | --- | --- |
| `remind_time` | `remind_at` | v1 只有 `HH:MM`，没有日期 |
| `createdAt` | `created_at` | 驼峰写法 |
| `updatedAt` | `updated_at` | 驼峰写法 |
| `title` / `content` | `text` | 只在 `text` 缺失时用作内容 |
| `remindDate` | `remind_date` | 驼峰写法 |
| 无 `id` | 生成新 id | 旧数据可能没有 id |
| `priority: "HIGH"` | `"high"` | 统一小写 |
| `done: true` 无 `done_at` | `done_at = updated_at` | 保证完成时间可展示 |
| 顶层无 `schema` | `schema = 2` | 读取时自动升级 |
| 顶层 `rev` | `version` | Python 端兼容读取，手机端只认 `version` |
| 顶层 `todos` 数组 | 同名字段 | 手机 v1 的 `local_todos` 是一个数组，读取时包装成 `{todos: [...]}` |
| 旧提醒无 `remind_date` | 按 `created_at` 当天解释 | 与 v1 行为一致；不会把“明天 9 点”误判成今天 |

注意：除 `createdAt` / `updatedAt` / `remindDate` 外，其它驼峰变体（如 `doneAt`）**不会**被识别；完成时间统一为 `done_at`。v1 的 `remind_time` 没有日期信息，升级后的旧提醒只会在创建当天那个时刻生效。

如果旧数据连 `created_at` 也没有（v1 手机端早期条目可能如此），归一化会填 `1970-01-01T00:00:00+00:00`；此时“按创建当天”实际是 1970-01-01，旧提醒不会到点。这类条目升级后需要重新设置提醒日期。

## 4. 时间与归一化规则

### 4.1 时间格式

统一用 **ISO8601 + 本地时区偏移 + 秒级精度**，例如 `2026-10-17T18:30:00+08:00`。

- Python 端 `to_iso()` 使用 `datetime.isoformat(timespec="seconds")`；
- 手机端 `toIso()` 手动拼出 `YYYY-MM-DDTHH:MM:SS±HH:MM`，不带毫秒；
- `parse_iso()` / `parseIso()` 额外接受 `Z` 结尾、`2026-10-17 18:30:00`、`2026-10-17 18:30`、`2026-10-17`；
- 无时区的旧值按**本机时区**解释；
- 比较时不看字符串字典序，统一转成 epoch 秒（`iso_rank` / `isoRank`），无法解析视为 0（最旧）。

### 4.2 归一化顺序

`normalize_doc(raw)` 的处理顺序固定：

1. 建立空文档 `{schema:2, version:0, updated_at:EPOCH, todos:[], tombstones:[]}`；
2. `todos`：逐条 `normalize_todo`，丢弃空文本/非对象，按 `id` 去重（**先出现的胜出**）；
3. `tombstones`：逐条要求对象、有 `id`、`deleted_at` 可解析，按 `id` 去重（先出现胜出）；
4. `version`：取整数，负数归 0；兼容 Python 的 `rev`；
5. `updated_at`：无法解析用 epoch；
6. `todos`、`tombstones` 按 `id` 升序排序。

因此同一份语义数据，无论字段顺序、空白、`null`/缺失如何，归一化后都相同。

### 4.3 边界值

| 输入 | 结果 |
| --- | --- |
| `text: "   "` | 条目被丢弃 |
| `remind_at: "25:99"` / `"9:00"` | `""`（必须两位小时） |
| `remind_date: "2026-13-40"` | `""` |
| `remind_at: "09:00"`, `remind_date: ""` | 保留；提醒日期按 `created_at` 的日期 |
| `done: true`, `done_at: ""` | `done_at = updated_at`（或 `created_at`） |
| `version: "7"` | Python 转成 7；JS `parseInt` 也是 7 |
| `tombstones` 里有重复 id | 只保留第一条合法记录 |
| 同 id 两条 todo | 只保留先出现的一条 |

## 5. 内容指纹 `canonical`

### 5.1 定义

`canonical(doc)` 先归一化，再只取**内容**（不含 `schema`、`version`、文档级 `updated_at`），生成紧凑、键有序的 JSON：

```text
payload = {
  "todos": [ <每条待办的 10 个字段，键名字母序> ],
  "tombstones": [ {"deleted_at": ..., "id": ...} ]
}
text = json.dumps(payload, ensure_ascii=False, sort_keys=True, separators=(",", ":"))
```

Python 的 `sort_keys=True` 把每条待办的键排成：

```text
created_at, done, done_at, id, notified_at, priority, remind_at, remind_date, text, updated_at
```

手机端没有 `sort_keys`，所以 `normalizeTodo` 的返回对象和 `canonicalItem` 都**手工按字母序插入键**，`JSON.stringify` 保持插入顺序，从而与 Python 输出逐字节一致。`todos`、`tombstones` 在归一化时已按 `id` 排序，`canonical` 里不再依赖对象键序。

交付前已做过交叉验证：同一份文档（含墓碑、完成态、提醒字段）分别交给 `core.canonical` 和浏览器端 `P.canonical`，输出逐字节一致。以后若增删字段，记得两端同步修改 `normalizeTodo` / `canonicalItem` 的键顺序，否则会出现“每轮同步都在 PATCH 但内容看起来没变”的问题。

示意（一行，实际是完整内容）：

```json
{"todos":[{"created_at":"2026-10-17T09:00:00+08:00","done":false,"done_at":"","id":"td-1","notified_at":"","priority":"high","remind_at":"18:00","remind_date":"2026-10-18","text":"交周报","updated_at":"2026-10-17T09:00:00+08:00"}],"tombstones":[]}
```

### 5.2 为什么忽略 `version` 和 `updated_at`

如果指纹包含 `version`，那么每轮 `merge_docs` 都会因为 `version+1` 而判定“内容变了”，导致无限 PATCH。文档级 `updated_at` 同理：每次合并都会刷新成 now。真正需要比较的是“条目集合 + 墓碑集合”。

### 5.3 指纹的用途

| 场景 | 用法 |
| --- | --- |
| 判断两端内容是否相同 | `docs_equal(a, b)` |
| 判断要不要推送 | `needs_push(local, remote)` |
| 同步窗口内本地是否又有新改动 | `canonical(merged) != canonical(remote)` |
| 测试锚点 | Node 测试断言 `canonical` 以 `{"todos":[{"created_at":` 开头、没有多余空格 |

若两端指纹算法不一致，典型症状是：**每 30 秒都在 PATCH，云端版本号一直涨，但内容看起来没变**。排查时先把同一份 JSON 分别喂给 `core.canonical` 和 `P.canonical` 比较输出。

## 6. 合并算法 `mergeDocs`

### 6.1 伪代码

```text
mergeDocs(local, remote):
    L = normalizeDoc(local)
    R = normalizeDoc(remote)

    # 1) 条目按 id 取并集，后写胜出
    todos = map(L.todos by id)
    for item in R.todos:
        current = todos[item.id]
        if current is null or rank(item.updated_at) >= rank(current.updated_at):
            todos[item.id] = item          # 相等时右侧（remote）胜

    # 2) 墓碑按 id 取并集，最新的 deleted_at 胜
    tombstones = map(L.tombstones by id)
    for tomb in R.tombstones:
        current = tombstones[tomb.id]
        if current is null or rank(tomb.deleted_at) > rank(current.deleted_at):
            tombstones[tomb.id] = tomb     # 相等时保留左侧

    # 3) 墓碑与条目决斗
    for id, tomb in tombstones:
        item = todos[id]
        if item is null: continue
        if rank(tomb.deleted_at) >= rank(item.updated_at):
            remove todos[id]               # 删除晚于/等于编辑 → 删除生效
        else:
            remove tombstones[id]          # 编辑晚于删除 → 条目复活

    # 4) 裁剪墓碑：180 天内、最多 200 条
    cutoff = now() - 180 天
    kept = [t for t in tombstones.values() if rank(t.deleted_at) >= cutoff]
    sort kept by deleted_at desc
    kept = kept[:200]

    # 5) 输出
    return {
        schema: 2,
        version: max(L.version, R.version) + 1,
        updated_at: now(),
        todos: sort by id,
        tombstones: sort by id
    }
```

### 6.2 胜负规则明细

| 情况 | 规则 | 结果 |
| --- | --- | --- |
| 两端都有同 id 条目 | `updated_at` 较大者胜；相等时**函数右参数**胜 | 一条内容，整条替换 |
| 只有一端有条目 | 直接取并集 | 新增保留 |
| 两端都有同 id 墓碑 | `deleted_at` 较大者胜；相等时**左参数**保留 | 一个墓碑 |
| 墓碑 vs 条目，`deleted_at >= updated_at` | 删除生效 | 条目移除，墓碑保留 |
| 墓碑 vs 条目，`deleted_at < updated_at` | 编辑更新 | 墓碑移除，条目保留（复活） |
| 两端都没有的 id | 无事发生 | — |

> “右参数胜”意味着调用顺序有语义。标准同步路径调用 `merge_docs(local, remote)`，所以**远端在时间相同时胜出**；电脑端同步完成后调用 `merge_docs(remote, self.doc)`，让同步窗口内的本地点击在时间相同时胜出。这不是矛盾，而是“同一秒内的平局由调用方决定”，两端不会因此产生不一致，因为下一次合并会按同样的比较收敛。

### 6.3 为什么时间相等时也要有确定结果

如果“相等就都保留”，`todos` 会出现两条同 id 记录，后续渲染、删除、墓碑决斗都会歧义。所以必须选一边。代价是：**同一秒内对同一条目的两次不同编辑，可能有一边被覆盖**。要避免这种情况，不要在两台设备上同时改同一条；或者接受条目级 LWW 的语义。

### 6.4 为什么墓碑要裁剪

墓碑是“删除的证据”，必须保留足够久让离线设备看到。但 Gist 文件不能无限增长，所以：

- 180 天：覆盖“电脑关机几个月再开”的常见场景；
- 200 条：即使频繁删除，文件也不会被墓碑撑爆；
- 先按 `deleted_at` 倒序保留最近 200 条，再按 `id` 排序输出。

超过窗口的墓碑被裁剪后，如果某台设备带着更旧的副本回来，条目可能复活。这是有意的取舍，不是 bug。

## 7. `needsPush`：什么时候写云端

```text
needsPush(local, remote) = canonical(mergeDocs(local, remote)) != canonical(remote)
```

含义：**把本地合并进远端后，内容是否与远端不同**。为真说明本地有远端没有的东西，需要 PATCH。

会返回真的情况：

- 本地新增了条目；
- 本地条目比远端同 id 条目更新；
- 本地有远端没有的墓碑；
- 本地的墓碑让远端某个条目被删除；
- 合并会裁掉远端过期墓碑（内容也会变）。

会返回假的情况：

- 只有 `version` / `updated_at` 不同；
- 两端内容完全一致；
- 本地比远端旧（合并结果就是远端）。

实际同步时的判断：

| 位置 | 判断 | 说明 |
| --- | --- | --- |
| 电脑 `GitHubGistStore.sync` 200 分支 | `needs_push(merged, remote)` | 合并后是否超出远端 |
| 电脑 `GitHubGistStore.sync` 304 分支 | `needs_push(local, remote)` | 用缓存的远端文档判断 |
| 手机 `syncNow` | `state.meta.dirty` 为真，或 `needsPush(merged, remote)` 为真 | 离线改动即使内容碰巧相同也强制推一次，确保 dirty 清除 |
| 电脑 `on_sync_finished` | `canonical(merged) != canonical(remote)` | 判断同步窗口内是否又有本地改动，决定 2.5 秒后补推 |

## 8. HTTP 交互

### 8.1 请求头

两端一致：

```http
Authorization: Bearer ghp_xxxxxxxx
Accept: application/vnd.github+json
X-GitHub-Api-Version: 2022-11-28
User-Agent: Win11TaskbarLyrics/1.1
```

手机端由浏览器自动加 `Origin` 等头，`User-Agent` 由浏览器决定；不要手动设置 `User-Agent`（浏览器会拒绝某些值）。

### 8.2 读取：GET `/gists/{gist_id}`

首次或没有 ETag：

```http
GET /gists/aa11bb22cc33 HTTP/1.1
Host: api.github.com
Authorization: Bearer ghp_xxx
Accept: application/vnd.github+json
X-GitHub-Api-Version: 2022-11-28
```

响应 `200` 的关键结构：

```json
{
  "id": "aa11bb22cc33",
  "files": {
    "taskbar_todos.json": {
      "filename": "taskbar_todos.json",
      "content": "{ ...文档 JSON... }",
      "truncated": false
    }
  }
}
```

同时响应头带 `ETag: "d3f4..."`。客户端把 `content` 字符串 `json.loads` / `JSON.parse`，再 `normalize_doc`。

带 ETag 的条件请求：

```http
GET /gists/aa11bb22cc33 HTTP/1.1
If-None-Match: "d3f4..."
```

- `304 Not Modified`：内容没变，**不计入 GitHub 限流额度**；客户端用上次缓存的远端文档继续合并；
- 冷启动就 304 且没有缓存远端文档：客户端会**去掉 ETag 再 GET 一次**（电脑端和手机端都实现了这个兜底）；
- `200`：更新 ETag 与远端缓存；
- 其它状态：按第 9 节映射错误。

### 8.3 写入：PATCH `/gists/{gist_id}`

```http
PATCH /gists/aa11bb22cc33 HTTP/1.1
Authorization: Bearer ghp_xxx
Accept: application/vnd.github+json
X-GitHub-Api-Version: 2022-11-28
Content-Type: application/json

{
  "files": {
    "taskbar_todos.json": {
      "content": "{\n  \"schema\": 2,\n  \"version\": 43,\n ...\n}"
    }
  }
}
```

- `content` 必须是**字符串**，不是嵌套对象；两端都对 `normalize_doc` 后的文档做 `json.dumps(..., ensure_ascii=False, indent=2)` / `JSON.stringify(doc, null, 2)`；
- 响应 `200`，带新的 `ETag`；客户端保存它，下一轮用作 `If-None-Match`；
- PATCH 是**整文件覆盖**，没有字段级合并；因此调用前必须先 GET + merge；
- 没有使用 `If-Match`：Gist API 不提供基于版本的原子写，强行加也用不上。并发覆盖靠下一轮合并收敛（见第 10 节）。

### 8.4 创建：POST `/gists`

```http
POST /gists HTTP/1.1
Authorization: Bearer ghp_xxx
Content-Type: application/json

{
  "description": "Win11 Taskbar Lyrics & Todo Sync Data",
  "public": false,
  "files": {
    "taskbar_todos.json": {
      "content": "{ ...初始文档... }"
    }
  }
}
```

响应 `201`，`id` 即 Gist ID。电脑端 `create_gist()` 与手机端 `createGist()` 都用 `public: false`。创建成功后：

- 电脑端：把 ID 填回设置对话框输入框，保存后重建 `GitHubGistStore` 并同步；
- 手机端：把 ID 写进配置并保存，然后同步。

### 8.5 ETag 与限流

| 项 | 说明 |
| --- | --- |
| 认证请求限额 | 每小时 5000 次（GitHub 对 authenticated user 的通用额度） |
| 304 是否计数 | **不计数**；条件请求返回 304 时不计入额度 |
| 30 秒轮询的代价 | 理论上每小时 120 次 GET；大部分是 304，实际消耗很小 |
| 手机端 60 秒轮询 | 每小时 60 次，叠加回前台/聚焦/联网触发 |
| 额外请求 | 每次真正变更一次 PATCH；创建 Gist 一次 POST |
| 限流表现 | `403`，响应头有 `X-RateLimit-Remaining` / `X-RateLimit-Reset`；程序只显示 403 文案，不解析重置时间 |
| 浏览器 ETag | GitHub 通过 CORS 暴露 `ETag`；若某浏览器拿不到，`etag` 为 `null`，退化为每轮 200 全量读取，正确性不受影响，只是更费额度 |

## 9. 错误码与异常映射

### 9.1 HTTP 状态

| 状态/条件 | 两端提示 | 根因 | 处理 |
| --- | --- | --- | --- |
| `401` | `GitHub Token 无效或已过期（401），请重新配置` | Token 错、过期、被撤销、复制少字符 | 重新生成 classic token（只勾 gist），两端更新 |
| `403` | `GitHub 拒绝访问（403，通常是限流或无 gist 权限）` | 没勾 `gist`；触发限流/滥用检测；组织策略 | 检查 Token scopes；等限流窗口；降低手动同步频率 |
| `404` | `Gist 不存在（404），请检查 Gist ID` | Gist ID 错、Gist 被删、Token 无权访问 | 核对 ID；用「创建新 Gist」重建并同步两端 |
| 其它 `4xx/5xx` | `GitHub API 请求失败（HTTP N）` | 服务端错误、代理、网络中间层 | 稍后重试；看日志 |
| 网络异常 | 电脑：`网络错误：<异常>`；手机：`Failed to fetch` 等 | 断网、DNS、代理、证书 | 恢复网络后下一轮自动重试 |

两端都把 401/403/404 映射成同一句中文，错误对象带 `status`（电脑 `GitHubApiError.status`，手机 `Error.message`），UI 据此提示。

### 9.2 内容与协议错误

| 条件 | 提示 | 说明 |
| --- | --- | --- |
| Gist 里没有 `taskbar_todos.json` | `Gist 中缺少 taskbar_todos.json 文件` | 填了别的 Gist，或文件被改名/删除 |
| `files[...].truncated == true` | `Gist 文件内容被截断（超过 1MB），请清理待办数据` | GitHub 对超过 1MB 的文件不返回完整内容；不要在这种情况下 PATCH，否则会用半份数据覆盖 |
| `content` 不是合法 JSON | `Gist 中的 JSON 解析失败：<原因>` | 手工编辑坏了、合并冲突残留；先备份再从 Gist 历史恢复 |
| 未配置 | `尚未配置 GitHub Token / Gist ID` | `configured` 为假；电脑端 `store is None` 时直接跳过同步 |
| 创建响应没有 `id` | `创建 Gist 成功但响应中没有 id` | 极少见；检查 GitHub 状态页 |
| 本地配置读写失败 | 日志警告，使用默认配置/空文档 | 不阻塞启动；检查 `%APPDATA%` 权限 |

关键安全行为：**读取失败时同步直接抛错，不会用本地文档覆盖云端**。JSON 损坏、截断、404 都不会触发 PATCH；这避免了“一个坏响应把云端清空”。

## 10. 并发与最终一致性

Gist 没有事务，两个客户端可能同时读到同一版本、各自 PATCH，后写的覆盖先写的。协议不阻止覆盖，而是保证**下一轮合并把被覆盖的内容找回来**。

### 10.1 两端同时新增不同条目

初始云端 `version=10`，只有 A、B：

| 时刻 | 手机 | 电脑 | 云端 |
| --- | --- | --- | --- |
| t1 | 离线新增 C | 离线新增 D | A、B（v10） |
| t2 | GET 得 A、B；merge 得 A、B、C；PATCH | — | A、B、C（v11） |
| t3 | — | GET 得 A、B、C；与本地 A、B、D merge 得 A、B、C、D；PATCH | A、B、C、D（v12） |
| t4 | GET 得 A、B、C、D；本地已有 C；merge 后不推送 | — | 收敛 |

交换 t2/t3 的顺序结果一样，因为并集满足交换律。

### 10.2 两端同时改同一条目

云端 A 的内容是“旧”，`updated_at=10:00`。

| 场景 | 手机编辑 | 电脑编辑 | 结果 |
| --- | --- | --- | --- |
| 手机后改 | 10:05 改成“手机版” | 10:04 改成“电脑版” | 手机版胜；电脑下一轮被覆盖 |
| 电脑后改 | 10:04 改成“手机版” | 10:06 改成“电脑版” | 电脑版胜；手机下一轮变电脑版 |
| 同一秒 | 10:05:00 手机版 | 10:05:00 电脑版 | 标准 `merge(local, remote)` 中远端胜；两端下一轮以先写入云端的为准，不保证两台同时编辑的内容都保留 |

同一条目是**整条替换**，不会把“手机版”和“电脑版”的文本做 diff 合并。需要保留两份时，请拆成两条待办。

### 10.3 删除与编辑冲突

云端 A 的 `updated_at=10:00`。

| 场景 | 删除方 | 编辑方 | 合并结果 |
| --- | --- | --- | --- |
| 删除更晚 | 手机 10:05 写墓碑 | 电脑 10:03 编辑后同步 | `deleted_at(10:05) >= updated_at(10:03)` → 删除生效，编辑丢失 |
| 编辑更晚 | 手机 10:05 写墓碑 | 电脑 10:06 编辑后同步 | `deleted_at(10:05) < updated_at(10:06)` → 编辑生效，墓碑被移除（复活） |
| 恰好相等 | 10:05 删除 | 10:05 编辑 | `>=` → 删除生效 |

“删除后又被编辑”会复活，这是有意的：用户在删除之后确实又修改了这条，说明它还需要存在。反过来，“编辑后又被删除”必须删除，否则墓碑永远打不过新编辑。

### 10.4 并发 PATCH 覆盖

两端都 GET 到 v10（A、B），都认为自己有新内容：

| 时刻 | 手机 | 电脑 | 云端 |
| --- | --- | --- | --- |
| t1 | PATCH A、B、C（v11） | — | A、B、C |
| t2 | — | PATCH A、B、D（v11，覆盖） | A、B、D（C 暂时丢失） |
| t3 | GET 得 A、B、D；本地有 C；`needsPush` 为真；merge 得 A、B、C、D；PATCH（v12） | — | A、B、C、D |
| t4 | — | GET 得 A、B、C、D；无新内容 | 收敛 |

前提是手机端在 t3 之前**没有清掉本地缓存**。如果手机重装了浏览器/清了站点数据，C 就真的丢了——这是“无服务器事务”的固有风险，重要数据请避免长时间离线只存一端。

### 10.5 304 与本地 dirty

- 手机离线改了 C，`dirty=true`；恢复网络后 GET 返回 304（云端没变）。`shouldPush = dirty || ...` 为真，仍然 PATCH，把 C 推上去；
- 电脑本地有 C，GET 返回 304；`needs_push(local, remote)` 为真 → `merge + PATCH`；
- 如果 304 但本地没有新内容 → 不写，省一次额度。

### 10.6 收敛的边界

协议保证的是“在没有清空本地缓存、没有超过墓碑 TTL、没有混用 v1.0 的前提下，经过有限轮同步后两端内容一致”。以下情况不保证：

| 情况 | 后果 |
| --- | --- |
| 一端清了 localStorage / 删了 `state.json` | 它丢失本地未推送内容，无法再并回去 |
| 离线超过 180 天 | 它的删除墓碑可能已被裁剪，旧条目可能复活 |
| 混用 v1.0 | v1.0 整份覆盖且不认识墓碑，删除可能丢失 |
| 两台设备时钟相差很大 | 旧编辑可能因 `updated_at` 更大而获胜 |
| 同一秒改同一条 | 一边内容被 LWW 覆盖 |
| Gist 文件被手工改坏 | 同步停止，不覆盖；需人工修复 |

## 11. 提醒语义

### 11.1 目标时刻

```text
reminder_datetime(todo):
    if remind_at 为空: return null
    hour, minute = remind_at
    if remind_date 合法: day = remind_date
    else: day = date(created_at)        # v1 兼容：按创建当天
    return local_datetime(day, hour, minute)
```

- `remind_at` / `remind_date` 是**本地墙钟**，不是 UTC 时间戳；在北京创建的“09:00”，到纽约后仍按当地 09:00 解释；
- 日期缺失时用 `created_at` 的日期（不是“今天”），避免旧数据在升级后被错误地当成今天；
- 目标时刻没有秒，按 `HH:MM:00` 处理。

### 11.2 到期判定

```text
due_reminder(todo, now):
    if todo.done: return false
    if todo.notified_at 非空: return false
    target = reminder_datetime(todo)
    if target is null: return false
    delta = now - target
    return 0 <= delta <= 24 * 3600
```

| 条件 | 含义 |
| --- | --- |
| `done` | 已完成不提醒 |
| `notified_at` 非空 | 已经提醒过（云端去重，重启/换电脑都不再提醒） |
| `0 <= delta` | 已到点（now ≥ target）；delta 为负表示还没到点，不提醒 |
| `delta <= 24h` | 距目标不超过 24 小时；更旧的提醒不再补 |

`upcoming_reminders(doc)` 取所有未完成且到期的条目，按目标时刻升序。电脑端每秒调用一次，维护一个提醒队列；同一时刻多条到期会逐条展示。

### 11.3 `notified_at` 的写入与清空

| 操作 | 对 `notified_at` 的影响 |
| --- | --- |
| 电脑端触发提醒 `_activate_next_alert` | 写入当前时间（先写本地，再尝试同步云端） |
| 手机端渲染 | 只读：非空显示「已提醒」，不写入 |
| 标记完成 | 保留原值（完成本身已足够抑制） |
| 取消完成（恢复未完成） | **清空**，允许再次提醒 |
| 稍后提醒 `snooze_todo` | **清空**，并把日期/时间改到 now+10 分钟 |
| 仅编辑提醒时间/日期 | **不清空**（标准编辑路径只改 `remind_at`/`remind_date`） |

最后一条是容易踩的坑：如果一条待办已经提醒过，你只把时间从 09:00 改到 10:00，`notified_at` 仍然非空，10:00 不会再提醒。需要再次提醒时，先把该条标记完成、再取消完成（`done=false` 会清空 `notified_at`），或删除后重建，或使用提醒弹出时的「10 分钟后再提醒」。

### 11.4 24 小时补提醒窗口

`REMIND_GRACE_SECONDS = 86400`。设计目的：

- 电脑晚上关机，第二天早上开机，昨晚 20:00 的提醒仍在窗口内，会补一次；
- 超过 24 小时的提醒不再打扰，但条目保留在列表中，用户可自己处理；
- 窗口从目标时刻算起，不是从“上次检查”算起。

### 11.5 稍后提醒

```text
snooze_todo(doc, id, minutes=10):
    target = now_local() + 10 分钟
    item.remind_at = target.HH:MM
    item.remind_date = target.YYYY-MM-DD
    item.notified_at = ""
    item.updated_at = now
    doc.version += 1
```

电脑端右键菜单「⏰ 10 分钟后再提醒」调用它；改完后立即 `save_state` + `request_sync`，手机端也能看到新时间。若跨过午夜，`remind_date` 会变成第二天日期。

### 11.6 手机端与电脑端的职责

| 端 | 职责 |
| --- | --- |
| 电脑端 | 真正的到点提醒：队列、红底闪烁、左键完成、稍后提醒、云端 `notified_at` |
| 手机端 | 只做展示：把 `dueReminder` 为真的条目标红（`alerting` 样式）、显示「已提醒」；不做系统通知、不在后台计时 |

因此“手机锁屏时会不会提醒”的答案是：不会，提醒由电脑端负责；手机页面关闭后也不会后台同步。

## 13. 版本演进与兼容

| 版本 | 文档形态 | 兼容性 |
| --- | --- | --- |
| v1.0 | `{updated_at, todos:[...]}`，无 `schema`/`version`/`tombstones`；条目用 `remind_time` 等旧字段 | v1.1 读取时自动归一化；v1.0 不认识墓碑 |
| v1.1 | schema 2：`schema/version/updated_at/todos/tombstones`，条目 10 字段 | 与 v1.0 可互相读取普通条目，但**删除会丢** |

升级建议：

1. 先备份 Gist 的 `taskbar_todos.json`；
2. 手机端与电脑端**同时**升级到 v1.1；
3. 触发一次实际变更（新增/编辑/完成/删除任一条）后，检查云端是否出现 `"schema": 2`、`"version": >0`、`"tombstones": []`；只打开页面或只同步不会改写云端文件；
4. 不要长期让 v1.0 与 v1.1 同时写同一个 Gist。

未来如果升到 schema 3，必须保证 v1.1 客户端在读取到不认识的 `schema` 时不会盲目覆盖；当前实现没有这个保护，升级前要先改两端。

## 9. 每日待办归属规则（v1.2.2）

「22:00 填明天、凌晨 2:00 自动翻篇」**不新增 schema 字段**：归属日期由条目的 `created_at` 按本地时间推导，Python（`core.todo_day`）与前端 JS（`protocol.todoDay`）算法相同，因此 Gist 里不需要存 `day`，旧数据也能直接套用。

| 创建时间（本地） | 归属日期 |
| --- | --- |
| 02:00–21:59 | 当天 |
| 22:00–23:59 | 第二天 |
| 00:00–01:59 | 当天（也就是前一晚 22 点后填的那一天） |

- **“今天”**（任务栏展示日）：02:00–23:59 的日历日；00:00–01:59 仍算前一天；
- 任务栏优先显示“今天”的未完成项；今天没有时退回最早的逾期项（文案前缀「⏰ 逾期」）；
- 22:00–01:59 且第二天没有任何未完成待办时：电脑端每天弹一次填写提醒（配置项 `last_fill_reminded` 去重）、任务栏副行显示提示；手机端页面顶部显示提示条；
- 该规则只影响桌面端展示与提醒，不改变同步/合并/墓碑协议，schema 仍为 `2`。

## 13. v1.3.0：schema v3 与账本协议

### 13.1 待办 schema v3

在 v2 基础上，每条 todo 新增三个字段（旧数据缺失时自动补默认值）：

| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `due_date` | string | `""` | 目标完成日期 `YYYY-MM-DD`；空=未指定 |
| `parent_id` | string | `""` | 父任务 id；空=独立任务 |
| `estimate_minutes` | int | `0` | 预计耗时（分钟），0=未估 |

- `todo_day(todo)` 优先用合法的 `due_date`，非法/空则回退 v2 的 `created_at` 规则；
- 归一化会过滤非法日期（如 2026-02-30）、自引用 parent；
- canonical 键仍按字母序，新增键位于 `created_at` 之后：`created_at, done, done_at, due_date, estimate_minutes, id, notified_at, parent_id, priority, remind_at, remind_date, text, updated_at`；
- 父任务显示 `[done/total]` 由两端分别按 `subtasks(parent_id)` 计算，不额外存储进度字段。

> 兼容性：v1.2.x 桌面端不认识 v3 字段，升级时请桌面端与 PWA 一起更新，否则旧端可能丢字段。

### 13.2 账本协议（独立 Gist，schema 1）

账本与待办**分开存**：账本使用自己的私密 Gist、文件名 `taskbar_ledger.json`，结构：

`json
{
  "schema": 1,
  "version": 0,
  "updated_at": "2026-10-20T18:52:12+08:00",
  "entries": [
    {"id": "lg-...", "date": "2026-10-20", "type": "expense", "amount": 12.5,
     "category": "餐饮", "note": "", "created_at": "...", "updated_at": "..."}
  ],
  "tombstones": [{"id": "lg-...", "deleted_at": "..."}]
}
`

- 合并规则与待办一致：条目级 `updated_at` 后写胜出 + `tombstones` 防复活；
- `amount` 统一保留两位小数；`type` 只能是 `income` / `expense`；
- `ledger_week_summary` 以周一为起点，返回收入/支出/结余/分类汇总/本周明细；
- canonical 序列化与前端 `canonicalLedger` 逐字节一致（金额按 Python float 风格）。

### 13.3 每日记忆与周报

- 每日记忆写入私有仓库 `taskbar-memory`，路径 `memories/YYYY-MM-DD.md`，索引 `memories/index.json`（按日期倒序、同日去重、最多 400 条）；
- **v1.3.2 起**：每天 **04:00** 推送**前一天**的记忆；程序当时未运行则下次启动自动补推（`last_memory_date` 记录已推送日期）；
- 周报同时可用于 Gmail 邮件，不写入 Gist；
- AI 评价由外部 OpenAI 兼容 API 生成，默认模型 `deepseek-flash`；仅在空闲时段（安静时段或系统 5 分钟无输入）调用，否则使用本地规则评价，不影响记忆/周报的其它内容。
